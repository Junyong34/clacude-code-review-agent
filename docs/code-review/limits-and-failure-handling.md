# 리뷰 입력 제한과 실패 처리

호출부 스니펫 제한은 Claude에게 전달할 코드 양을 정합니다. 스니펫 하나는 보통 변경 함수를 사용하는 함수의 본문 또는 일부입니다. 원본 소스를 수정하는 제한이 아니며 상한을 넘었다고 PR 리뷰를 중단하지 않습니다.

## 다섯 가지 스니펫 제한

상수와 적용 코드는 [`symbolReference.ts`](../../src/services/codeReview/symbolReference.ts)에 있습니다. 환경변수로 조정하는 설정은 아닙니다.

| 제한 | 상수 | 값 | 쉽게 설명하면 |
|---|---|---|---|
| PR당 개수 | `MAX_CALLER_SNIPPETS_PER_PR` | 20개 | 여러 변경 함수의 스니펫을 모두 합해 20개까지 |
| 심볼당 개수 | `MAX_CALLER_SNIPPETS_PER_SYMBOL` | 5개 | 변경 함수 하나의 사용 코드를 5개까지 |
| 스니펫당 라인 | `MAX_CALLER_SNIPPET_LINES` | 60줄 | 긴 함수는 심볼이 처음 등장하는 지점 주변만 선택 |
| 전체 본문 문자 수 | `MAX_CALLER_SNIPPET_TOTAL_CHARS` | 30,000자 | 다음 스니펫을 넣어 초과하면 그 스니펫을 건너뜀 |
| 한 줄의 코드 문자 수 | `MAX_CALLER_SNIPPET_LINE_CHARS` | 300자 | 앞 300자만 남기고 ` …`를 붙임 |

문자 수는 코드의 JavaScript 문자열 `length` 기준입니다. 전체 본문 예산에는 붙인 라인 번호도 포함하지만 `[REF]` 헤더와 `[REF-CALLER]` 표시는 포함하지 않습니다. 한 줄 상한은 라인 번호를 붙이기 전 원본 코드에 적용합니다.

이 제한들은 동시에 적용됩니다. breaking 계열 판정을 먼저, `unknown`을 다음으로 처리하므로 변경 함수마다 공평하게 5개씩 배분하지 않습니다. 구현만 변경됐거나 호환 가능한 변경으로 판정한 심볼은 스니펫 대상에서 제외합니다.

## A를 사용하는 함수가 25개라면

CRG가 호출부 위치 25개를 찾았고 모두 이번 PR에서 수정되지 않았다고 가정합니다. 심볼당 상한 때문에 A의 코드는 최대 5개만 첨부하고 나머지 최소 20개는 생략합니다. 앞선 심볼이 PR 예산을 사용했거나 문자 수 제한, 파일 읽기 실패가 있으면 5개보다 적을 수도 있습니다.

| 출력 | 제공 범위 |
|---|---|
| Claude의 `[REF]` | 댓글 대상 심볼의 조회된 참조 파일 목록 |
| Claude의 `[REF-CALLER]` | 제한 안에서 수집한 호출부 코드 |
| 최종 CRG 참조 안내 | 스니펫 유무와 관계없이 댓글 대상 참조 파일을 파일별로 묶어 표시 |

스니펫 제한 때문에 CRG 댓글의 파일 목록을 자르지는 않습니다. 같은 파일에 여러 호출 함수가 있어도 파일 항목은 하나로 묶습니다. 이미 PR에서 변경한 파일과 구현만 변경된 심볼 등의 제외 규칙은 계속 적용됩니다. CRG가 찾지 못한 참조까지 안내한다고 보장하지 않습니다.

## Claude는 생략된 수량을 아는가

현재 입력은 실제 발견 개수, 제공 개수, 생략 개수와 생략 이유를 명시하지 않습니다. 프롬프트에는 긴 함수가 일부만 제공된다는 설명과 보이지 않는 호출부를 추측하지 말라는 규칙이 있습니다. 하지만 `25개 중 5개 제공` 같은 커버리지 정보는 넣지 않습니다.

이 규칙은 일부 증거를 전체 검증 결과로 일반화하지 않도록 하는 지시이며 오답 방지를 보장하지 않습니다. 생략된 호출부에서만 발생하는 문제는 놓칠 수 있습니다. 제공되지 않은 사용처가 정상이라고 단정할 근거도 없습니다. 현재 별도의 호출부 추가 리뷰나 생략 정보 전달 단계는 없습니다.

## diff와 master의 범위

- diff 주변 문맥은 25줄을 요청합니다. 긴 CONTEXT 구간은 `[OMITTED]`로 압축하고 한 줄이 청크 예산보다 길면 앞부분만 남깁니다. [청크 설명](claude-input-and-streaming.md)을 참고하세요.
- 호출부와 그래프는 최신 master 기준입니다. PR 브랜치의 신규 코드와 다른 브랜치의 변경을 직접 읽지 않습니다.
- 변경 전 위치를 잡을 수 없는 순수 삽입이나 그래프에 없는 관계는 참조를 놓칠 수 있습니다. 구형 스키마에서는 파일 목록만 조회할 수 있습니다.
- master와 PR diff 기준이 다르면 인터페이스 판정이 `unknown`일 수 있습니다. 판정은 모든 호출자를 실행한 결과가 아닙니다.
- 청크별 Claude 요청은 독립적입니다. 다른 청크의 코드까지 모두 확인한 결과로 읽어서는 안 됩니다.

## 단계별 실패 처리

실행 제어는 [`prReview.ts`](../../src/services/codeReview/prReview.ts), 응답 파싱과 오류 분류는 [`codeReview.ts`](../../src/services/codeReview/codeReview.ts), 댓글 요청은 [`bitbucket/index.ts`](../../src/services/bitbucket/index.ts)를 기준으로 합니다.

| 상황 | 처리 |
|---|---|
| 동일 PR 실행 중 | 추가 실행을 건너뜀 |
| 자동 리뷰 완료 시그니처 발견 | 자동 리뷰를 건너뜀 |
| 최초 활동 조회 실패 | 오류 안내를 시도하고 종료 |
| diff 조회 실패 또는 Bitbucket `truncated` | 안내 댓글을 시도하고 종료 |
| CRG 준비나 조회 실패 | 일반 모드에서는 증거 없이 Claude 리뷰 계속 시도 |
| 호출부 파일 읽기 실패 | 해당 스니펫 없이 진행 |
| `CODE_REVIEW_CRG_ONLY=true` | Claude 없이 CRG 결과만 게시, 스니펫 파일 읽기도 생략 |
| 청크에 리뷰할 내용 없음 | 안내 댓글을 시도하고 종료 |
| Claude 요청/스트림 실패 | 남은 청크 처리와 결과 게시 중단, 오류 안내 댓글 시도 |
| `budget_exceeded` | 이미 계산한 CRG 결과만 댓글로 게시 시도 |
| Guardrail 차단 | 리뷰 중단, 설정된 리뷰 Slack URL에 차단 알림 시도 |
| JSON 파싱 실패 | 해당 청크를 안내 요약과 빈 인라인 의견으로 대체하고 계속 진행 |
| JSON 파싱 실패에서 출력 잘림 추정 | 빈 인라인 의견으로 대체하고 최종 댓글에 잘림 안내 추가 |
| 게시 전 기존 댓글 조회 실패 | 인라인 게시를 시작하지 않고 오류 안내 시도 |
| 인라인 댓글 하나의 API 실패 | 로그를 남기고 다음 의견과 최종 댓글 게시 계속 |
| 최상위 댓글 API 실패 | 오류 안내 댓글을 시도하고 실패로 종료 |

모든 청크 처리가 끝나기 전에는 인라인 의견을 게시하지 않습니다. 청크 호출 중 실패하면 일부 청크의 의견만 먼저 남는 일은 없습니다. 게시 단계에서는 API가 개별적으로 실패할 수 있어 일부 댓글만 남을 수 있습니다. 최종 댓글의 의견 개수는 게시 대상 개수이며 API 성공 개수를 별도로 집계하지 않습니다.

일반 실패 안내와 CRG 전용 댓글에는 완료 시그니처를 넣지 않습니다. 다만 JSON 파싱 실패는 예외 대신 안내 결과로 대체하므로 최종 댓글과 완료 시그니처 게시까지 진행될 수 있습니다. 구조화된 의견이 없더라도 전체 검증이 성공했다고 해석하지 않아야 합니다.

## 동시성의 경계

PR 잠금과 Claude 스트림 제한은 프로세스 내부에 있습니다. Git과 CRG 갱신은 동시성 1로 직렬화하지만 이후 그래프와 파일 조회는 그 잠금 밖입니다. 여러 프로세스의 같은 워크트리 공유와 리뷰 중 다른 갱신까지 보호하지 않습니다. 서버 재시작 후 이어서 처리하는 영속 작업 큐도 이 파이프라인에 없습니다.
